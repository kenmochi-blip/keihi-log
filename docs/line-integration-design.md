# LINE連携機能 設計ドキュメント

作成日: 2026-07-04 / ステータス: 設計中（実装前レビュー用）

## 0. 目的とスコープ

LINE公式アカウント（bot）に領収書画像を送ると、送信者の経費ログに登録される機能。
非IT層・Googleアカウントを持たないメンバーでも「LINEで送るだけ」で経費申請できるようにし、
チームプランへの切り替え動機を作る。

### やること（初期版）
- 画像送信 → AI解析 → **確認/修正/やめる** → 登録
- 登録前の各種監査アラート（重複・高額・AI解析額との不一致 等）
- 「未精算」等のキーワードで自分の未精算一覧を返信（read-only）
- 管理者が発行する**連携コード**によるメンバー紐付け

### やらないこと（初期版）
- Push通知（承認/精算のお知らせ）← 課金回避。**Push/Multicast/Broadcast/Narrowcast API は一切使わない**
- LINE上での承認・精算・削除・編集（Webで行う）
- LINEでの交通費・領収書なし申請
- リッチメニュー等の作り込み

### 料金前提（2026-07-04 LINE公式サポートAIで確認）
- 無料プラン（コミュニケーションプラン）月200通。
- **Reply API / 応答メッセージ / あいさつメッセージ / LINEチャットは通数カウント外**。
- カウント対象は Push / Multicast / Broadcast / Narrowcast。
- → **全応答を Reply API に限定**すれば無料枠を消費しない。

## 1. プラン制御

- LINE機能は**チームプラン限定**（トライアル中も可）。
- 強制点は**連携コード発行時のみ**。設定シートB3→`license:{key}`をKVで読み、`plan==='team' || trial===true` を検証。
- 既存のWeb側メンバー管理のプラン挙動（現状クライアントのみ制限）には**手を付けない**。
- ダウングレード/解約後: 既存紐付けは、Webhook受信時にプランを都度確認し、非チームなら丁寧に拒否メッセージ（Reply）を返す。

## 2. 識別モデル（併用前提）

**LINE連携は「メンバーの種類」ではなく「メンバーの属性」**。既存メンバー（メールあり）もLINE連携できる。

- メールありメンバーがLINE連携 → LINE経由の申請も **P列=本人のメール** で記録。Web/LINEで同一の行に集約。合成IDの波及なし。
- **メールなしメンバー（LINE専用）のみ**合成IDを使う。
  - 合成IDフォーマット: `line:{sha256(userId)先頭12文字}`（生userIdはシートに書かない）
  - マスタ表A列=名前、B列（メール欄）に合成IDを格納 → 既存の `getMemberName` / メンバー別集計がそのまま動く
  - 権限（D列）は member 固定
- CSV「申請者Email」列に合成IDが出るため、管理者向けに見せ方は実装時に調整（表にはほぼ出ない＝後変更も軽微）。

## 3. KVキー設計

| キー | 値 | TTL | 用途 |
|---|---|---|---|
| `line:code:{code}` | `{sheetId, memberEmail_or_synthId, name}` | 24h | 連携コード（6桁・使い捨て・発行時にセット） |
| `line:code_try:{code}` | 試行回数(int) | 24h | 総当たり対策（10回で無効化） |
| `line:link:{userId}` | `{sheetId, identity, name}` | 無期限 | userId→メンバー紐付け（本体） |
| `line:pending:{userId}` | `{解析結果, imageHash, driveFileId, step}` | 10分 | 登録前の確認/修正の会話状態 |
| `line:evt:{eventId}` | `1`（NXロック） | 1h | Webhook冪等化（リトライ二重処理防止） |
| `line:rl:{userId}` | レート制限カウンタ | 60s | 連投からのクォータ保護（_rateLimit流用） |

- 紐付けの逆引き（メンバー削除時に消すため）: `line:link_by_sheet:{sheetId}` に userId 一覧をセットで保持。

## 4. エンドポイント構成（api/data/[...path].js に集約）

関数12個制限のため新規ファイルを作らず、キャッチオール内にルートを追加。

| メソッド/パス | 認証 | 内容 |
|---|---|---|
| `POST /api/data/line/webhook` | LINE署名検証（生ボディ必須） | LINEからのイベント受信。全処理の入口 |
| `POST /api/data/line/code` | 既存 `_authorize`（admin） | 連携コード発行（設定タブから呼ぶ） |
| `POST /api/data/line/unlink` | 既存 `_authorize`（admin） | 連携解除（メンバー削除連動でも呼ぶ） |

- `LINE_ENABLED` 環境変数がOFFなら webhook は即200（no-op）を返すキルスイッチ。
- 署名検証: `x-line-signature` を `LINE_CHANNEL_SECRET` でHMAC-SHA256検証。生ボディが要るのでStripe webhookと同じbodyParser回避パターンを流用。

## 5. Webhook処理フロー（状態遷移）

### 5-1. 連携コード受信（テキストが6桁数字）
1. `line:code:{code}` を読む → 無ければ「コードが無効です」Reply
2. 試行回数チェック（`line:code_try`）
3. 有効 → `line:link:{userId}` を作成、コード削除 → 「連携しました。◯◯チームの△△さんとして登録されます」Reply

### 5-2. 画像受信
1. eventId で冪等化（NXロック）。取得済みなら無視
2. `line:link:{userId}` を確認 → 未連携なら案内Reply、終了
3. プラン確認（sheetId→license）→ 非チームなら案内Reply、終了
4. レート制限チェック
5. LINEコンテンツAPIで画像取得 → SHA-256計算 → SAで証票フォルダ（設定B4）へ保存
6. サーバー版Geminiプロキシ（設定B5のキー使用）で解析
7. **監査チェック（§6）**を実行
8. `line:pending:{userId}` に解析結果+ハッシュ+driveFileId+監査結果を保存（TTL10分）
9. 解析結果+監査アラート+クイックリプライ `[登録する][修正する][やめる]` をReply

### 5-3. ボタン: 登録する
1. `line:pending` を読む（無ければ「時間切れです。もう一度画像を送ってください」）
2. 既存の書き込み処理（`expensesCreate`相当）を `_withSheetWriteLock` 内で実行
   - P列=メール or 合成ID、B列=名前、A列=サーバー時刻、監査結果→K列、AI解析額→N列
3. `line:pending` 削除 → 「登録しました（申請済）」Reply

### 5-4. ボタン: 修正する
1. `[日付][支払先][金額][科目][戻る]` をReply
2. 項目選択 → `line:pending.step` を更新 → 「新しい値を送ってください」Reply
3. 値受信 → パース（全角/カンマ許容）→ pending更新 → 更新後の内容+`[登録する][修正する][やめる]` をReply
4. 科目は設定のカテゴリをSAで読みボタン化（最大13個・超過は「その他は文字で」）

### 5-5. ボタン: やめる / 10分放置
- pending削除。放置時は何もReplyしない（通数ゼロ）。

### 5-6. キーワード「未精算」等
1. `line:link` 確認 + **マスタ表メンバーシップ再検証**（キャッシュだけ信用しない）
2. `readExpensesViaSA` で自分の未精算（L列空）を抽出 → 直近N件+件数+合計をReply

## 6. 監査ロジックのサーバー移植

現状クライアント（submit.js `_runAuditChecks`）にあるチェックをサーバー側の共有関数として新規実装。

移植対象:
- インボイス番号+金額+日付の重複
- 同一画像ハッシュの重複
- 同日・同額・類似取引先
- 10万円以上の高額
- AI解析額と申請額の不一致（→N列保存も同様に）
- 2ヶ月以上前の日付

**二重管理の扱い（合意済み）**: 初期版はサーバー側を新規作成しWebと併存。
CLAUDE.mdに「監査ルール変更時は submit.js とサーバー側の両方を直す」と明記。
将来Web側もサーバー監査を呼ぶ1本化を**次の課題**として記録。

## 8. 環境変数（追加）

- `LINE_CHANNEL_SECRET` — 署名検証用
- `LINE_CHANNEL_ACCESS_TOKEN` — Reply API 呼び出し用
- `LINE_ENABLED` — キルスイッチ（"1"でON）

開発用・本番用でチャンネルを分けるため、プレビュー環境と本番環境で別の値を設定。
